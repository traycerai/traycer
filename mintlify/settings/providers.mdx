**Providers** settings control the coding agents Traycer can run on a host. They apply to the host selected with the host switcher at the top of the Settings sidebar; see [Host Picker](/settings#host-picker).

For which coding agents Traycer supports and what each one can do, see [Agents & Models](/agents-and-models/coding-agents).

## Provider List

The list on the left shows every provider, with the enabled ones first.

- **Search providers** narrows the list by name.
- **Filter providers** shows **All**, **Enabled**, or **Disabled** providers.
- **Refresh all providers** checks sign-in and CLI status again.

Select a provider to open its tabs.

## Turn A Provider On Or Off

The switch in the provider's header reads **Enabled** or **Disabled**. Only enabled providers appear in the composer's model picker.

- Claude Code and Codex are enabled in a new install.
- Other providers, except Traycer Inference, can turn on automatically when the host starts and verifies their credentials. If verification fails, a later host start can try again. Signing in during a session does not turn a provider on by itself.
- Once a provider has an enabled or disabled setting, host startup preserves it. You can change it with the switch.
- **Traycer Inference** is opt-in. It uses Traycer credits, so only you can turn it on.

At least one provider must stay enabled. A provider with managed profiles needs at least one enabled profile before you can turn it on.

## Account

The **Account** tab holds the API key for providers that authenticate with one.

| Status               | Meaning                                                                            |
| -------------------- | ---------------------------------------------------------------------------------- |
| **Not set**          | No key is stored, and none was found in your shell environment.                    |
| **Key set**          | A key is stored in Traycer.                                                        |
| **From environment** | Traycer is using the key's environment variable from your shell.                   |

Paste a key and click **Save**. A stored key is encrypted on the host and overrides the one in your shell. When a key is stored, the field reads **Replace stored key…**, and **Clear** removes it. Some providers show a **Create an API key** link to their dashboard.

| Provider     | Environment variable |
| ------------ | -------------------- |
| Cursor       | `CURSOR_API_KEY`     |
| Kiro         | `KIRO_API_KEY`       |
| Droid        | `FACTORY_API_KEY`    |
| OpenRouter   | `OPENROUTER_API_KEY` |
| Hugging Face | `HF_TOKEN`           |
| Amp          | `AMP_API_KEY`        |

## Managed Profiles

Claude Code, Codex, Grok, and Antigravity can hold more than one account. The provider's own CLI login, the one you would use in a terminal, is the **Terminal account**. Managed profiles are extra accounts next to it.

<Steps>
  <Step title="Add the profile">
    On **Profiles & Limits**, click **Add profile**.
  </Step>
  <Step title="Name it">
    Give the profile a name and a color.
  </Step>
  <Step title="Link the account">
    Click **Link account** and sign in to the account this profile should use.
  </Step>
</Steps>

Each profile has its own switch, so you can turn one off without removing it. A profile's menu lets you rename it, change its color, sign in again, or remove it.

What a new profile shares with the Terminal account depends on the provider:

| Provider    | Shared with the Terminal account                                                                                                                                              | Kept separate                                           |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Claude Code | Session history, `settings.json`, `CLAUDE.md`, agents, commands, and hooks. Skills and plugins too, if you check **Use terminal skills and plugins** when you add the profile. | The account sign-in                                     |
| Codex       | Sessions, history, and skills                                                                                                                                                 | `auth.json`, and the profile's own copy of `config.toml` |
| Grok        | Nothing                                                                                                                                                                       | Everything                                              |

Grok profiles use separate `GROK_HOME` directories, so each profile keeps its OAuth account, configuration, and sessions isolated. New profiles start with an empty private store: ambient configuration, MCP credentials, plugins, skills, memory, and sessions are not copied. Ambient xAI API keys and external-auth commands are not inherited by managed Grok profiles.

Antigravity’s Terminal account can use Google sign-in or inherit `GEMINI_API_KEY` from your shell. A managed profile uses its own Google sign-in or stored Gemini API key; it does not inherit the shell’s key. Signing a profile out never touches the Terminal account.

To pick a profile for the next turn, use the profile dropdown in the composer's model picker. It appears once a provider has two or more profiles.

### Sync Profiles Across Devices

Use **Sync profiles…** on **Profiles & Limits** to copy the profiles on the host selected in Settings to your other devices. Sync covers Claude Code, Codex, Grok, and Antigravity profiles. It copies the sign-in itself, so a synced profile is ready to use on the other device without signing in again.

The dialog lists your other devices. For each one:

- **Sync now** copies every supported profile to that device once.
- **Keep in sync** also sends profiles you add later, and name and color changes, as they happen. Turning it off keeps the profiles already on the device. An offline device catches up when it connects.

Closing the dialog doesn't stop a sync. A Terminal account arrives as a regular profile, and the other device's own Terminal account is never changed. Once a profile is synced, a sign-in that refreshes on one device is passed to the other, so neither is signed out.

Under each device, every profile has one status: **Synced**, **Syncing**, **Sign in needed**, **Device offline**, **Update needed**, or **Can't sync** with the reason. Profiles that need attention are listed first, and **Show all** lists the rest. After you fix a **Can't sync** reason, click **Sync now** to try again.

- **Sign in needed**: the profile is signed out on the device you are syncing from. The button on that row opens its sign-in there.
- **Is now signed in to a different account**: you switched the account on the device the profile was synced from. The other device keeps the old account until you click **Sync the new account**.
- **Are signed in to different accounts**: the account was switched on the device that received the profile. Sync never replaces either account. Sign in to the same account on both devices to resume.

## Signing In Again

When a provider is signed out, the composer shows a banner above the input.

- **Authenticate** (for example **Authenticate Claude Code**) opens your browser to sign in. If the browser doesn't return on its own and shows a code, paste the code into the banner.
- Providers that sign in from a terminal offer a terminal sign-in instead.
- "Or paste an API key or token" takes a key or token directly, for providers that accept one.
- **Check sign-in status** checks again after you sign in somewhere else.

If the agent's profile is signed out, the banner offers **Continue on Terminal account** and **Sign in**. If the profile no longer exists, it offers **Manage in Settings**.

Browser sign-in runs on the machine the host is on. For a host on another machine, sign in with that provider's CLI there.

## CLI Binary And Arguments

The **CLI & Args** tab chooses which binary Traycer runs for the provider:

- the copy Traycer manages for you,
- a copy found on your `PATH`, or
- a binary you point to with **Add custom path**.

For CLIs that Traycer manages, open the version menu on the managed row to see the available versions.

- **Download**, **Use**, and **Delete** act on one version.
- **Use** pins that version. A pinned provider shows "Pinned to" its version; **Use latest automatically** removes the pin.
- **Check for updates** looks for a newer version, and **Auto-download updates** downloads new versions as they come out.

Traycer does not manage the Amp, Hermes Agent, or Command Code CLIs; install them yourself, then pick the detected copy or add its path.

For Claude Code, Codex, and OpenCode, this tab also has **Terminal interface CLI arguments**. They are appended to the CLI when you start an agent on the Terminal interface, and they pre-fill the launch picker, where you can change them for one launch. Use bypass or auto-approval flags deliberately. Codex permission flags such as `--approve-for-me`, `--ask-for-approval`, and `--sandbox` apply when a session starts; when Traycer reopens or forks a Codex session, the session keeps its own permissions, so Traycer leaves those flags out.

### Model List Timeout

The **Model list** group on the **CLI & Args** tab sets how long Traycer waits for the provider to list its models: when you open the model picker, and when an agent creates another agent. **Timeout** offers **60 s** (the default), **90 s**, **120 s**, and **180 s**. Pick a longer one on a slow or heavily loaded machine, where a provider can take more than a minute to answer.

With **Same for all providers** on, the timeout is shared: changing it changes every provider whose switch is also on. Turn the switch off to give this provider its own timeout, which starts at the shared value; turn it back on to follow the shared value again.

A change applies from the next model list the host reads, and a model list that arrives after the wait is still kept for the next request. The group is hidden on a host running a version without per-provider timeouts.

## Environment Variables

The **Env** tab sets environment variables for one provider. Each row has a name and either **Set** with a value, or **Unset** to drop a variable inherited from your shell. They apply when Traycer starts that provider.

For Cursor, these variables reach only its configuration commands, such as MCP setup, and not chat turns.

Shell-wide host environment variables live in [Shell](/settings/shell).

## Permissions

The **Permissions** tab shows who reviews this provider's commands in Auto mode. Where the provider has a reviewer of its own, a switch chooses between it and Traycer's judge; otherwise the tab shows which one applies. **All permission settings** opens [Permissions](/settings/permissions#providers-with-a-built-in-reviewer).

## Model Providers

OpenCode reaches models through upstream providers, which you manage on its **Model Providers** tab.

- **Connect** a provider by signing in or with an API key. The dialog lists the sign-in methods that provider offers.
- **Disconnect** removes a provider's credential.
- **Add custom provider** adds an OpenAI-compatible endpoint: a **Provider ID**, **Display name**, **Base URL**, optional **API key**, its **Models**, and optional **Headers**.
- **Manage Go** opens your OpenCode Go account.

## MCP Servers

Add and check provider-specific tool servers in the **MCP** tab. See [MCP servers](/settings/providers/mcp-servers).

## Plugins

Click **Add from source**, enter a **Source** (an npm package, a path, a git URL, or `plugin@marketplace`), and click **Install**. The location picker at the top chooses whether a plugin applies to every workspace on the host or to one workspace. Restart the provider's running agents for plugin changes to reach active sessions.

## Skills

Import or write reusable instructions in the **Skills** tab. See [Skills](/settings/providers/skills).
